### КАК ПРОХОДИТ ХАКАТОН: 

Хакатон проводится в течение 5 дней 

В течение этого времени команды проходят этапы разработки, промежуточные проверки (CheckPoint) и финальную защиту проекта 

Каждый день включает практическую работу и контроль прогресса со стороны экспертов. 

Финалъная цель – создать рабочий продукт и представить его экспертам

- Python запускается `python3 --version`
- Git работает `git --version`
- Docker работает `docker --version`
- Docker запускает контейнер `docker run hello-world`
- Работает установка пакетов через `pip`
- Есть доступ к своему личному GitHub аккаунту
- Git настроен (указаны user.name и user.email)
- Интернет-соединение стабильное

На финальной защите:
- Подготовьте презентацию проекта (задача, архитектура, результат). 
- Обязательно расскажите про распределение ролей в команде. 
- Покажите уникальность вашего решения — чем оно отличается и почему именно ваш подход лучше.

## КОНКУРСНОЕ ЗАДАНИЕ 

### БИЗНЕС-КОНТЕКСТ 

Современный университет — это цифровая экосистема с большим объёмом данных: студенты, преподаватели, учебные планы, аудитории, приёмная кампания, отчётность для руководства. Все данные хранятся в PostgreSQL и используются для аналитики и управления процессами. 

### ОДНАКО: 
- данные представлены в виде таблиц БД; 
- для получения информации требуется знание SQL; 
- сотрудники тратят значительное время на подготовку отчётов; 
- приёмная комиссия перегружена однотипными вопросами; 
- отсутствует удобный и безопасный инструмент доступа к данным; 
- неконтролируемые запросы могут перегружать систему. 

**ЦЕЛЬ** 

Университету требуется интеллектуальный ассистент, который обеспечит безопасный, масштабируемый и контролируемый доступ к данным через естественный язык. 

### РАЗГРАНИЧЕНИЕ ДОСТУПА И ПЕРСОНАЛЬНЫЕ ДАННЫЕ 

Система обязана соблюдать ограничения по работе с персональными данными 

**[Разрешено выводить: (галочка)]**
- ФИО преподавателей; 
- ФИО деканов; 
- ФИО сотрудников университета 

**[Запрещено выводить: (крестик)]**
- персональные данные студентов; 
- персональные данные абитуриентов; 
- паспортные, контактные и иные чувствительные данные; 
- любые данные, позволяющие идентифицировать обучающихся. 

Все ответы должны предоставляться в агрегированном или обезличенном формате, если речь идёт о студентах или абитуриентах

## БАЗОВЫЙ КЕЙС (ОБЯЗАТЕЛЬНЫЙ) 

### Суть задания 

Разработать Al-ассистента для анализа данных PostgreSQL, реализующего связку: 

Вопрос пользователя → LLM → SQL → Проверка → Выполнение → Корректный ответ 

Это базовая версия интеллектуального коннектора «строка подключения → безопасный чат с БД» 

Главный фокус: 
- корректность, 
- безопасность, 
- стабильность работы. 

### ЛОГИКА РАБОТЫ 

**[1] Пользователь вводит вопрос в чат**

**[2] Система:**
- получает схему базы данных; 
- передаёт её в LLM; 
- генерирует SQL-запрос.

**[3] Перед выполнением запроса:**
- проверяется, что это SELECT; 
- проверяется whitelist таблиц; 
- автоматически добавляется LIMIT; 
- применяется statement_timeout.

**[4] Запрос выполняется в PostgreSQL**

**[5] Пользователь получает:**
- понятный ответ; 
- отображение SQL; 
- результат в виде таблицы.

**[6] При ошибке:**
- возвращается корректное сообщение; 
- данные не «придумываются».

### ПОЛЬЗОВАТЕЛИ СИСТЕМЫ 

Система предназначена для использования разными категориями пользователей: 

**АБИТУРИЕНТЫ** 
- получение информации о направлениях подготовки; 
- количество бюджетных и платных мест; 
- статистика прошлых лет (в агрегированном виде); 
- сроки подачи документов; 
- средний проходной балл прошлых лет.

**СТУДЕНТЫ** 
- просмотр собственной успеваемости; 
- средний балл за семестр; 
- наличие академических задолженностей; 
- список дисциплин текущего семестра; 
- расписание занятий.

**ПРЕПОДАВАТЕЛИ** 
- список своих дисциплин; 
- количество студентов в группах; 
- средний балл по дисциплине; 
- процент неаттестованных; 
- учебная нагрузка по семестрам.

**СОТРУДНИКИ И АДМИНИСТРАЦИЯ** 
- численность студентов по факультетам; 
- статистика приёма; 
- динамика набора по годам; 
- отчётность по кафедрам; 
- заполняемость аудиторного фонда; 
- статистика отчислений (без ФИО студентов); 
- нагрузка преподавателей.

**[ВАЖНО:]** 
Студенты могут получать только обезличенные данные (количество мест, перечень направлений обучения и тд). 
Данные других студентов выводятся исключительно в агрегированном или обезличенном виде.

## КРИТЕРИИ ПРИЁМКИ (ОБЯЗАТЕЛЬНЫЕ) 

**Функциональность** 
- Работает подключение к PostgreSQL. 
- Реализован цикл Text → SQL → выполнение → ответ. 
- SQL отображается пользователю. 
- Поддерживается LIMIT. 

**Безопасность** 
- Разрешены только SELECT-запросы. 
- Запрещены INSERT / UPDATE / DELETE / DROP / ALTER. 
- Реализован whitelist таблиц. 
- Есть защита от SQL-инъекций. 
- Настроен statement_timeout. 
- Соблюдается политика персональных данных. 

**Точность** 
- В промпт передаётся схема БД. 
- Корректная работа с JOIN и агрегатами. 
- Нет «галлюцинаций». 
- Ошибки обрабатываются корректно. 

**Производительность** 
- В LLM не передаются большие массивы данных. 
- Применяется ограничение количества строк. 
- Контролируется размер ответа. 

**Пользовательский опыт** 
- Реализован чат-интерфейс. 
- Есть поле ввода и кнопка отправки. 
- Отображается история сообщений. 
- Есть индикатор загрузки. 
- Результат выводится в виде таблицы.

## КРИТЕРИИ ОЦЕНКИ РЕШЕНИЯ 

Оценка проектов проводится по нескольким ключевым направлениям. Каждое направление отражает как техническое качество реализации, так и соответствие бизнес-задаче. 

### 1. ТЕХНИЧЕСКАЯ АРХИТЕКТУРА 
Оценивается зрелость и качество инженерного решения. 
- Асинхронность — обработка запросов без блокировок. 
- Логирование — фиксация всех действий пользователя и системных событий. 
- Параллелизм — поддержка одновременной работы нескольких пользователей и запросов. 
- Тестирование — наличие тестов, проверяющих корректность и стабильность работы. 

### 2. РЕШЕНИЕ БИЗНЕС-КЕЙСА (РЕЗУЛЬТАТ) 
Оценивается, насколько система решает поставленную задачу. Система должна уметь: 
- принимать вопрос на естественном языке; 
- генерировать корректный SQL; 
- выполнять запрос к PostgreSQL; 
- возвращать понятный ответ; 
- работать в интересах сотрудников и абитуриентов; 
- соблюдать политику персональных данных; 
- быть встраиваемой как чат-виджет. 

Главный показатель — реальная работоспособность и польза решения 

### 3. ПРОИЗВОДИТЕЛЬНОСТЬ 
Оценивается скорость и эффективность работы. 
- Скорость ответа в цепочке: вопрос → LLM → БД → ответ. 
- Контроль объёма выборки. 
- Отсутствие передачи больших массивов данных в LLM. 
- Стабильная работа под нагрузкой. 

### 4. БЕЗОПАСНОСТЬ 
Оценивается защищённость системы и данных. 
- Только SELECT-запросы. 
- Whitelist таблиц. 
- Защита от SQL-инъекций. 
- statement_timeout. 
- Соблюдение политики персональных данных (вывод только разрешённых данных, без раскрытия данных студентов и абитуриентов). 

### 5. ПРОГРЕСС ЗА ДЕНЬ 
Оценивается динамика и продуктивность работы команды. 
- Объём выполненной работы. 
- Стабильность развития проекта. 
- Достижение промежуточных результатов. 

### 6. КОМАНДНАЯ РАБОТА 
Оценивается слаженность и организация команды. 
- Распределение ролей. 
- Эффективность взаимодействия. 
- Совместное решение задач. 
- Качество коммуникации внутри команды.
